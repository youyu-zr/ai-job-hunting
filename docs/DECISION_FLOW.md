# AI 求职流程：原来怎么做，现在为什么这样改

本文解释程序实际在哪一步作判断、在哪一步执行动作。它不是“AI 永远不会误判”的保证；部署、自动测试和真实账号验收分别见[项目状态](PROJECT_STATUS_2026-10-16.md)。

## 先认识五个部分

| 部分 | 在这个项目里负责什么 |
| --- | --- |
| 浏览器脚本，也叫前端 | 在本人打开的 BOSS 网页中读消息、显示状态，并执行允许的发送动作 |
| 服务器程序，也叫后端 | 验证身份、保存账号偏好和会话状态、调用模型、决定允许什么动作 |
| AI 模型 | 结合消息、岗位、简历和偏好，理解含义、分类并生成普通回复 |
| 数据库 | 保存账号资料、个人偏好和持久会话状态，不依赖某一个浏览器标签页一直打开 |
| 个人偏好 | 描述你的求职条件和沟通习惯；未填写的事实不能由 AI 编造 |

“AI 认为应该做什么”和“程序真正执行什么”必须分开。模型可以建议一个动作，程序仍要检查动作是否合法、当前是否暂停、状态有没有在生成期间改变。

## 从登录到发送

1. 你登录自己的 BOSS 账号，脚本等待当前身份可用。
2. 服务端核验身份，再自动创建空账号、开通当前内测权限，不需要激活码。
3. 空账号不等于有简历。开始自动投递或开启 AI 坐席前，需要本人主动导入简历。
4. 筛岗位时，服务器结合岗位资料、简历和偏好判断。普通信息不足并不等于有风险，可以先沟通。
5. 收到 HR 消息后，先确认是谁发给谁的，再整理同一轮消息，提交给服务端判断。
6. 服务端先处理技术错误、明确风险、需要本人确认的决定，再考虑普通回复和简历请求。
7. 只有允许自动处理时，才生成回复或安排简历交换。浏览器发送前再次检查当前开关、会话暂停和状态版本。
8. 生成了一段文字，不等于已经发送。程序需要结合平台的响应判断动作结果；结果不确定时不能冒充成功或盲目重复发送。

这条链路仍需要真实账号从头走一遍。代码测试不能证明 BOSS 当前网页、平台登录状态和实际收发已经全部兼容。

## 例子一：为什么重要决定不能只写在提示词里

假设 HR 说：“请把简历发来，再确认是否接受这份报价。”

**原来的处理方式：** 程序已有一些暂停判断，但主要依赖固定表达。例如联系方式、薪资、地点和面试等话题可能触发接管；表达不在已覆盖范围时，又可能继续走“索要简历”或“生成回复”的分支。

**为什么会出问题：** “谈到某个话题”和“要求本人作出承诺”不是一回事。普通询问可能被过度暂停，而换一种说法的真实承诺又可能漏过。只告诉聊天模型“不要替用户答应”，也不能替代发送前的程序控制。

**现在的单次请求链路：**

```text
HR 消息 + 岗位 + 简历 + 已保存偏好
                  |
               AI 分类
                  |
          程序检查完整分类结果
                  |
       明确风险 -> 阻断当前岗位
       本人确认 -> 保存当前会话暂停状态
       普通沟通 -> 才进入回复/简历处理
```

模型返回“需要本人确认”时，后端先保存暂停状态，再结束这次自动处理，不先生成或发送“好的，我接受”。

**对用户的结果：** 你处理这个 HR 的决定，其他没有暂停的会话可以继续。处理完后点“恢复当前会话”，才重新允许这个会话自动运行。恢复按钮不是“我同意这个面试/报价”，也不会直接代发原来的确认。

**仍有局限：** 模型仍可能理解错误；旧有合同词法兜底还可能对否定句产生不必要的暂停。后者属于误暂停，不应被宣传成已经解决了所有语义判断。

## 例子二：为什么同一轮两条消息要一起判断

假设 HR 连续发来两条消息：“请确认明天上午十点面试”和一个“索要简历”的卡片。

**修复前的具体问题：** 浏览器按消息类型把普通文字和卡片分成两批，同时处理。文字那批正在等待 AI 判断时，卡片那批可能先处理完；它查询暂停状态时，另一批还没有来得及保存暂停，于是存在先发送简历的路径。

这叫并发时序问题：每个流程单独看似乎都检查了状态，但两个流程同时跑，检查的先后顺序仍可能错。

**修复要求：** 同一会话、同一合并窗口的消息要作为一轮安全判断，保留每条卡片的协议信息。不能只让两种消息排队，因为“索要简历先到、重要决定后到”的同一轮消息仍可能漏过。

**预期结果：** 不论这两条在同一窗口内谁先到，都先看完整一轮内容，再决定是否允许动作；面试卡片不能因为前面有一条普通文字就失去本人确认规则。不同 HR 的会话不应互相堵塞。

这不表示程序能够预知以后尚未收到的消息，也不能替代真实浏览器的时序验收。

## 例子三：为什么“看起来像正确答案”还不够

AI 返回的不只是聊天文字，还会返回供程序执行的分类结果，例如“正常招聘，可以回复”。

**修复前：** 分类解析会从模型回答中截取第一个看起来完整的 JSON 对象。外层套数组、对象后面多一个逗号或额外内容时，里面那段仍可能被接受。

**为什么不合适：** 程序需要的是一份符合约定的完整决策，不是从一段不合格回答中挑出一块能解析的片段。否则后面加的内容或输出结构错误就被丢掉了。

**修复后：** 使用完整 JSON 解析，必须只有一个对象、没有额外内容，再检查字段、类别和动作。完整的 JSON Markdown 代码块可以去掉外层格式后校验；任意解释文字、多结果或格式破损都不能直接放行。

第一次格式错误时，只能用原始输入重新分类一次；第二次仍不合格就暂不执行。不能不断重试，直到碰巧得到“可以发送”为止。

## 哪些按偏好，哪些需要本人

| 示例 | 处理原则 |
| --- | --- |
| “薪资大约 6K，可以聊聊吗？” | 结合已保存偏好沟通，不仅因出现薪资话题就暂停 |
| “工作地点在上海，可以吗？” | 结合已填地点要求；没有填写不能替你编造接受条件 |
| “方便留微信吗？” | 按本人已保存的联系方式偏好处理，不编造联系方式 |
| “面试通常分几轮？” | 普通流程咨询，不等于接受具体面试安排 |
| “请确认明天上午十点来面试” | 具体时间安排，需要本人确认 |
| “是否接受这个 offer / 确认签署合同？” | 明确承诺，需要本人确认 |
| “合同通常签几年？” | 普通合同信息询问，不等于签约 |
| “加群领取课程资料，报名后安排工作” | 结合上下文判断是否推广，普通推广默认不回复 |
| “先交费用才能入职 / 发展下线返佣” | 明确高风险优先阻断，不能靠普通偏好取消保护 |

这里描述处理原则，不是保证模型对每一种说法都分类正确。

## 例子四：断线后为什么会漏回复

去重机制是为了避免同一句 HR 消息反复触发 AI。原来处理开始时就会先记一个“正在处理”的标记；如果随后模型或网络失败，却没释放标记，下次恢复时就可能被当成“这条已经处理过”。

修复后，可重试的失败会释放这次处理占位，让后续有机会重新处理；已确认发送或结果不确定的简历交换不能因此盲目重发。

浏览器恢复后，补扫会先问服务器“这个账号的 AI 坐席是否开启”，再检查当前可识别联系人中最后一条是否来自 HR。本人已经回复、会话已暂停、身份不清楚或状态无法确认时，不猜测着发送。

因此它不是“把所有历史聊天逐条重新回复一遍”，也不是“断开前的旧草稿一律补发”。实际能读到哪些联系人，仍受当前 BOSS 页面提供的信息影响。

## 回退和协作是什么意思

Git 的每次提交记录一份代码状态；PR 是把一批修改送到指定分支合并的入口。自动检查，也叫 CI，会在另一台干净机器上重新运行测试和构建。

合并 PR 不等于重启服务器。服务器需要单独更新构建产物；反过来，服务器运行新版也不证明 GitHub 默认分支已经更新。

不需要把已知不可用旧版当作“稳定版本”继续维护。保留 Git 历史，是为了以后能定位和撤销某次新改动；真实账号验收通过后，才能把对应版本称作可用基准。

源码回退也不能撤回已发给 HR 的消息、已经交换的简历或已经发生的数据变化。这正是发送前必须检查和本人确认的原因。
