## 本地候选行为说明

以下是 `0.0.117` 本地候选代码的目标/实现说明，不代表线上 `0.0.116` 已具备这些行为，也不等于真实模型准确率或真人验收通过。

- **浏览器**读取 BOSS 页面中的职位、消息、发送者和结构化协议元数据，并执行经服务端决策后的页面动作；模型 API Key 留在服务器端。
- **服务器 AI**结合完整 HR 消息、岗位上下文、简历和用户偏好作语义分类。普通 HR 文本不会因为“系统”“抖音”“收费”等关键词而被浏览器直接丢弃。
- **岗位信息不全**：薪资、地点或公司细节缺失，但没有明确风险或已填写偏好冲突时，候选行为是继续投递，并留下后续可询问的问题。
- **推广偏好**：借招聘面向求职者的普通引流默认静默；用户可以编辑是否允许普通推广进入回复。明确高风险保护不受此偏好覆盖。普通抖音运营、市场、销售或推广岗位不因单个词过滤。
- **薪资、地点、联系方式**按用户保存的偏好判断；未填写时按未知处理，可向 HR 询问，不编造条件、不擅自承诺或泄露联系方式。
- **本人确认**：具体面试日期/时间、结构化面试卡片和明确接受 offer/签约等承诺交回本人，只暂停当前会话，不关闭账号级坐席。
- **BOSS 系统事件**可显示为会话气泡或卡片，但不是 HR 自然语言消息；脚本依据已知协议类型等元数据处理，不靠普通文案关键词识别。
- **AI/API/格式故障**不自动投递或发送，不伪装为岗位风险；提供可重试错误状态。

## 文档范围与已知限制

本轮 Task 7 只同步用户说明、数据流、验收用例和项目状态文档；不修改 Task 4/6 实现代码，不运行生产部署。新验收案例仍是待执行的验收要求，不是通过记录。完整运行测试可能受同一 worktree 中 Task 4/6 的并行代码修改影响，具体结果记在 Task 7 报告。

尚未解决的发布门槛：

1. 维护者核实 BOSS 对第三方浏览器脚本和自动收发消息的当前规则/授权；
2. 维护者确认并审查当前代码候选，修复/完成并行中的 Task 4/6；
3. 把候选推送后，为该确切提交运行远端 CI/CodeQL；
4. 给发布分支启用保护，明确必须通过 PR、检查和维护者审核；
5. 完成真实 BOSS 账号的登录、建档、导简历、投递、消息分类、人工接管、断线恢复和多设备验收；
6. 以上门槛通过后，才可按备份、原子替换、仅重启 `ai-job.service`、线上哈希复核和回滚流程部署。

“本地测试通过”“远端 CI 通过”“维护者批准”“真实 BOSS 账号验收”“已部署”是五种不同状态，不得相互替代。一个通过的旧 PR 检查不代表新候选通过；HTTP 200 也不代表业务健康、平台授权或真实用户可用。
