# AI 工作猎手宣传素材

状态：待版本发布和入口确认后使用。本文按普通求职者、AI 开发者两条内容线编写，不把两类人塞进同一条广告。

## 先说清楚

- 普通用户宣传的是：使用维护者托管服务时，不需要自己申请或填写模型 API Key。
- 自部署宣传的是：拉源码后，需要自己准备数据库和模型服务配置。
- 不能把“下载即用”写成完全本地运行；浏览器脚本需要脚本管理器和 BOSS 账号，简历导入后的数据处理位置要在发布时明确。
- 当前线上旧脚本与本地候选版不是同一个版本。候选版完成部署、真实账号验收、数据说明和发布门槛前，不发布普通用户安装召集。
- 没有真实群号、二维码或稳定社区地址前，不写“进粉丝群”，先用 GitHub Issues 作为反馈入口；群入口确认后再替换占位符。
- 当前这份不是“现在就能安装”的通知。普通用户版要等线上切换并验收后发布；开发者版要等候选源码同步、许可说明和自部署文档准备好后发布。

## 内容策略

### 内容支柱

1. **具体求职痛点**：职位看得多，但不容易判断是否值得继续；每个岗位都要重新组织第一句话；HR 对话多了容易丢上下文。
2. **实际功能演示**：岗位辅助筛选、岗位化首句、HR 普通消息处理、发送状态记录、关键节点人工确认。
3. **使用边界**：AI 是副驾，不替用户承诺面试、联系方式、薪资、到岗或录用。
4. **开源共建**：普通用户反馈使用问题，开发者提交脱敏 Issue、测试和 PR。

### 平台打法

- **抖音**：前 3 秒直接说一个具体卡点，15-30 秒只演示一个功能，最后只留一个行动。
- **小红书**：先定封面承诺，再写短段落正文；产品封面优先使用真实界面截图，暂时没有通过验收的真实截图时，不用 AI 伪造产品界面充当证据。
- **开发者内容**：单独成篇，讲 Issue/PR 怎么参与，不与求职者安装文案混写。

### 优先选题与复用

1. **求职者主内容**：用真实脱敏演示展示“一个岗位如何从职位详情到匹配判断、首句草稿和本人确认”。这是安装转化内容，但只能在正式版本和安装入口验收后发布。
2. **求职痛点切片**：每条只讲一件事，例如岗位判断、首句起草或 HR 上下文，不把全部功能塞进 30 秒。
3. **开发者教程**：用真实 GitHub 页面解释 Issue、Fork、PR，再展示项目里适合新贡献者的测试/文档任务。
4. **工程进展**：展示一次真实问题、修复和回归测试，避免只讲“AI 改变求职”这类空话。

先录一段真实产品演示，再拆成一条抖音、一个小红书轮播和一张 GitHub README 动图；每个平台重写开头和 CTA，不直接复制同一段长文。

### 复盘指标

- 抖音：前 3 秒留存、完播率、评论质量、主页访问。
- 小红书：封面点击、收藏、分享、评论里出现的真实求职问题。
- 转化：安装页访问、用户反馈、有效 Issue、可复现问题和被合并 PR。
- 没有真实用户数据前，不写提升百分比、安装人数、成功率或“大家都在用”。
- 每周只挑表现最好和最差的内容，调整一个变量：开头、演示功能或 CTA。不要为了追踪转化而把求职者数据偷偷接入第三方分析。

### 小红书正文

很多人看到开源项目，愿意帮忙，但会卡在一个问题：Issue、Fork、PR 到底分别是什么？

用 AI 工作猎手举例：

**Issue**：你发现问题，或者有一个功能建议。先写清楚现象、复现步骤和环境，不需要改代码。

**Fork**：把项目复制到自己的 GitHub 仓库，方便你在自己的副本里修改。

**PR**：你改完代码、文档或测试后，告诉维护者“这份改动可以请你审阅了”。

最简单的参与方式是：

1. 先提一个脱敏 Issue；
2. 熟悉代码后 Fork 并创建分支；
3. 改完带测试结果，再提 PR。

普通用户使用托管服务时不需要填写模型 Key；自部署和二次开发才需要自己准备数据库、模型服务和私有 Key。维护者的生产 Key、用户数据和服务器权限不会放进仓库。

这个项目第一批更需要的贡献，不一定是“大功能”：

- BOSS 页面兼容记录；
- 消息解析回归测试；
- 安装和启动文档；
- 前端错误状态；
- 自部署问题复现。
